构建系统与配置

掌握 West、CMake、Kconfig 和设备树，驾驭 Zephyr 的完整构建流程

West 多仓库管理工具

West 是什么？

West 是 Zephyr 官方的多仓库管理工具，你可以把它理解为"更聪明的 git submodule"。传统的 git submodule 在处理多个仓库的依赖关系时非常笨拙——更新麻烦、冲突频发、分支管理混乱。而 West 通过一个中心化的 manifest 文件来统一管理所有仓库的版本和路径，让多仓库协作变得井井有条。

West 的名字来源于 Zephyr 项目所在地——美国西风岭（Westerly），它也是 Python 包，通过 pip 安装：

bash 
pip install west

West 工作区结构

使用 West 初始化后的工作区（workspace）结构如下：

text 
my-workspace/
├── .west/                  # West 管理目录
│   └── config              # West 配置文件
├── zephyr/                 # Zephyr 主仓库（manifest-repo）
│   ├── west.yml            # 核心清单文件
│   ├── boards/             # 开发板定义
│   └── ...
├── modules/                # 外部模块
│   ├── hal/                # 硬件抽象层
│   ├── crypto/             # 加密库
│   └── ...
└── application/            # 你的应用代码

west.yml 清单文件

west.yml 是整个工作区的"蓝图"，它定义了需要拉取哪些仓库、从哪里拉取、拉取哪个版本。来看一个典型的 west.yml：

yaml 
# west.yml - Zephyr 项目的清单文件
manifest:
  remotes:
    - name: zephyrproject-rtos
      url-base: https://github.com/zephyrproject-rtos
    - name: my-company
      url-base: https://github.com/my-company

  projects:
    - name: hal_stm32
      revision: main
      remote: zephyrproject-rtos
      path: modules/hal/stm32

    - name: my-driver
      revision: v2.1.0
      remote: my-company
      path: modules/my-driver

  self:
    path: zephyr

关键概念：

  • remotes：定义远程仓库的 URL 前缀，类似于"通讯录"，避免重复写长 URL
  • projects：声明需要管理的子仓库，指定名称、版本（revision）和存放路径
  • self：指明 manifest 文件所在的仓库本身的位置

常用 West 命令

bash 
# 初始化工作区（拉取 zephyr 和所有依赖）
west init https://github.com/zephyrproject-rtos/zephyr

# 更新所有仓库到 manifest 指定的版本
west update

# 构建项目
west build -b nrf52840dk_nrf52840 ./my-app

# 重新构建（不清除缓存）
west build -b nrf52840dk_nrf52840 ./my-app --pristine

# 烧录固件
west flash

# 启动调试器
west debug

# 查看工作区中所有项目状态
west list

# 查看当前 manifest 信息
west manifest --freeze

提示：当你切换分支或更新 west.yml 后，务必执行 west update 来同步所有子仓库到正确的版本。否则可能出现编译错误，因为代码和依赖版本不匹配。

West 与 Git Submodule 的区别
特性Git SubmoduleWest
版本管理每个 submodule 独立记录 commit中心化 manifest 统一管理
依赖解析不支持支持项目间依赖关系
部分克隆不支持支持 west update --fetch-opt
构建集成无内置 build/flash/debug 命令
多清单合并不支持支持 import 机制合并多个清单

CMake 构建系统详解

Zephyr 如何使用 CMake

Zephyr 选择 CMake 作为构建系统，这和很多嵌入式项目使用 Makefile 直接构建不同。Zephyr 在 CMake 之上封装了一层自己的 API，让你不需要手写复杂的 CMake 规则就能管理源文件、头文件路径和编译选项。

当你执行 west build 时，实际上 West 是在调用 CMake 和 Ninja/Make 来完成构建。整个流程可以简化为：

text 
west build
  └─→ cmake -B build -GNinja -DBOARD=nrf52840dk_nrf52840 ...
      └─→ ninja -C build

CMakeLists.txt 结构

每个 Zephyr 应用的根目录下都有一个 CMakeLists.txt，这是构建的入口点。最简单的 CMakeLists.txt 长这样：

cmake 
cmake_minimum_required(VERSION 3.20.0)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(my_app)

target_sources(app PRIVATE src/main.c)

关键行解释：

  • find_package(Zephyr)：找到 Zephyr 的构建系统，加载所有 Zephyr 提供的 CMake 模块
  • project(my_app)：声明项目名称
  • target_sources(app PRIVATE ...)：向 app 目标添加源文件，app 是 Zephyr 预定义的构建目标

添加多个源文件

cmake 
cmake_minimum_required(VERSION 3.20.0)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(sensor_demo)

target_sources(app PRIVATE
    src/main.c
    src/sensor.c
    src/ble.c
    src/display.c
)

# 添加头文件搜索路径
target_include_directories(app PRIVATE src/include)

zephyr_library() — 创建库

当项目变大时，把代码组织成库是更好的做法。Zephyr 提供了 zephyr_library() API 来创建库：

cmake 
# 创建一个名为 my_lib 的库
zephyr_library(my_lib)

# 向库中添加源文件
zephyr_library_sources(
    my_lib/init.c
    my_lib/processing.c
)

# 向库中添加头文件路径
zephyr_library_include_directories(my_lib/include)

# 为库设置编译选项
zephyr_library_compile_definitions(MY_LIB_DEBUG)

构建类型

Zephyr 支持多种构建类型，通过 CMake 变量 CONF_FILE 或命令行参数控制：

bash 
# Debug 构建（默认，包含调试信息，无优化）
west build -b nrf52840dk_nrf52840 -- -DCONFIG_DEBUG=y

# Release 构建（开启优化，去除调试信息）
west build -b nrf52840dk_nrf52840 -- -DCONFIG_RELEASE=y

# 使用自定义 conf 文件
west build -b nrf52840dk_nrf52840 -- -DCONF_FILE=prj_release.conf

提示：开发阶段使用 Debug 构建，方便断点调试。发布时切换到 Release 构建，固件体积更小、运行更快。也可以通过 -DOVERLAY_CONFIG=debug.conf 叠加额外配置。

Kconfig 配置系统

Kconfig 是什么？

Kconfig 是 Zephyr 的配置系统，它就像餐厅的菜单——菜单上列出了所有可选的菜品（功能模块），你可以根据自己的口味（需求）来选择。每道菜可能还有前提条件（比如点了火锅才能加蘸料），这对应 Kconfig 的依赖关系。

通过 Kconfig，你可以精确控制哪些功能被编译进固件，哪些被排除。这对于资源受限的嵌入式设备至关重要——每一字节 Flash 都很珍贵。

prj.conf 配置文件

prj.conf 是项目的主配置文件，所有 CONFIG_ 开头的选项都在这里设置：

conf 
# 串口驱动 - 必须开启才能使用 UART
CONFIG_SERIAL=y

# GPIO 驱动 - 控制引脚输入输出
CONFIG_GPIO=y

# 蓝牙功能
CONFIG_BT=y
CONFIG_BT_PERIPHERAL=y
CONFIG_BT_DEVICE_NAME="My Zephyr Device"

# 日志系统
CONFIG_LOG=y
CONFIG_LOG_DEFAULT_LEVEL=3

# 调试选项
CONFIG_DEBUG=y
CONFIG_STACK_USAGE=y

配置值的类型有三种：

  • 布尔型：=y（启用）或 =n（禁用），如 CONFIG_SERIAL=y
  • 整型：=数字，如 CONFIG_LOG_DEFAULT_LEVEL=3
  • 字符串：="值"，如 CONFIG_BT_DEVICE_NAME="My Device"

menuconfig 交互式配置界面

如果你不确定有哪些配置选项，或者想浏览所有可用的配置，可以使用 menuconfig——一个类似 BIOS 设置界面的交互式工具：

bash 
# 在已构建的项目中打开 menuconfig
west build -t menuconfig

在 menuconfig 中，你可以：

  • 按 / 搜索配置项名称
  • 按 ? 查看当前选项的详细说明和依赖关系
  • 用空格键切换布尔值的开关状态
  • 用回车键进入子菜单或编辑数值

提示：在 menuconfig 中修改配置后，按 Q 退出并保存，配置会写入 build/zephyr/.config。记得把需要的配置同步到你的 prj.conf 中，否则下次构建时配置会丢失。

如何查找可用的配置选项

除了 menuconfig，你还可以通过以下方式查找配置选项：

  • 在 Zephyr 源码中搜索 Kconfig 文件，每个模块都有自己的 Kconfig 定义
  • 查看 官方 Kconfig 文档
  • 使用 west build -t guiconfig 启动图形化配置界面（需要 Python tkinter）

依赖解析

Kconfig 的依赖机制确保你不会启用一个功能却忘了它的前置条件。比如，启用蓝牙外设角色需要先启用蓝牙：

kconfig 
# 在 Zephyr 源码中的 Kconfig 定义
config BT
    bool "Bluetooth support"

config BT_PERIPHERAL
    bool "Peripheral Role"
    depends on BT          # 依赖 BT 先被启用

如果你在 prj.conf 中写了 CONFIG_BT_PERIPHERAL=y 却没有 CONFIG_BT=y，Kconfig 会自动帮你启用 CONFIG_BT，并给出提示。这就是依赖解析的作用——防止配置冲突和遗漏。

⚠️ 常见陷阱

有时候你明明在 prj.conf 中设置了 CONFIG_XXX=y，但构建时却没有生效。这通常是因为该选项被其他依赖条件"强制关闭"了。检查方法：在构建目录中查看 build/zephyr/.config，搜索你的选项，看它最终值是什么以及被什么影响。

设备树 Device Tree 详解

设备树是什么？

设备树（Device Tree，简称 DT）是描述硬件信息的数据结构。你可以把它想象成一张"硬件地图"——它告诉操作系统：这块板子上有什么芯片、每个芯片连在哪个引脚上、时钟频率是多少、有哪些外设等等。

使用设备树的好处是：硬件描述和驱动代码分离。同一个驱动程序可以适配不同的板子，只需要修改设备树中的参数，而不需要改驱动代码。这就像同一个导航软件可以适配不同城市的地图一样。

设备树文件类型

text 
boards/arm/nrf52840dk_nrf52840/
├── nrf52840dk_nrf52840.dts       # 板级设备树（主文件）
├── nrf52840dk_nrf52840.dtsi      # 芯片级设备树（SoC 共用）
└── nrf52840dk_nrf52840.overlay   # 覆盖文件（应用层自定义）
  • .dts：设备树源文件，描述特定开发板的硬件
  • .dtsi：设备树包含文件（类似 C 语言的 .h），通常描述芯片 SoC 级别的硬件，被 .dts 文件 include
  • .overlay：覆盖文件，用于在应用层修改或扩展板级设备树，不会修改原始板级文件

设备树基本结构

dts 
/* nrf52840dk_nrf52840.dts 简化示例 */
/dts-v1/;

#include <nordic/nrf52840_qiaa.dtsi>

/ {
    model = "Nordic nRF52840 DK";
    compatible = "nordic,nrf52840dk-nrf52840";

    chosen {
        zephyr,console = &uart0;
        zephyr,shell-uart = &uart0;
        zephyr,sram = &sram0;
        zephyr,flash = &flash0;
    };

    leds {
        compatible = "gpio-leds";
        led0: led_0 {
            gpios = <&gpio0 13 GPIO_ACTIVE_LOW>;
            label = "Green LED 0";
        };
    };

    aliases {
        led0 = &led0;
    };
};

/* 配置 UART0 节点 */
&uart0 {
    compatible = "nordic,nrf-uart";
    status = "okay";
    current-speed = 115200;
    tx-pin = 6;
    rx-pin = 8;
};

关键概念解读：

  • compatible：兼容字符串，是驱动匹配的"身份证号"。驱动程序通过 compatible 字符串找到对应的设备节点
  • chosen：Zephyr 特有的节点，用来指定系统默认使用的设备（如控制台用哪个 UART）
  • aliases：别名，让应用代码可以通过通用名称引用设备
  • status：设备状态，"okay" 表示启用，"disabled" 表示禁用

在 C 代码中访问设备树

Zephyr 提供了一组宏来在编译时读取设备树信息。这些宏以 DT_ 开头，在编译时展开为常量，没有运行时开销：

c 
#include <zephyr/kernel.h>
#include <zephyr/device.h>
#include <zephyr/drivers/gpio.h>

/* 通过 nodelabel 获取设备树节点 */
#define LED0_NODE DT_NODELABEL(led0)

/* 从节点获取 GPIO 信息 */
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(LED0_NODE, gpios);

/* 通过路径获取节点 */
#define MY_SENSOR DT_PATH(soc, i2c_40003000, sensor_temp)

/* 获取 compatible 字符串 */
#define SENSOR_COMPAT DT_NODE_FULL_NAME(MY_SENSOR)

int main(void)
{
    /* 检查 GPIO 设备是否就绪 */
    if (!device_is_ready(led.port)) {
        return -1;
    }

    /* 配置 LED 引脚为输出 */
    gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE);

    while (1) {
        gpio_pin_toggle_dt(&led);
        k_msleep(500);
    }

    return 0;
}

Overlay 文件 — 自定义板级配置

当你需要修改开发板的设备树配置（比如换一个引脚、增加一个 I2C 设备），不要直接修改板级 .dts 文件——那是 Zephyr 源码的一部分，升级版本时会被覆盖。正确做法是使用 .overlay 文件：

dts 
/* boards/nrf52840dk_nrf52840.overlay */

/* 在 I2C 总线上添加一个温度传感器 */
&i2c1 {
    status = "okay";

    temp_sensor: sensor@48 {
        compatible = "sensirion,sht3xd";
        reg = <0x48>;
        label = "SHT3XD";
    };
};

/* 修改 LED0 的引脚 */
&led0 {
    gpios = <&gpio0 15 GPIO_ACTIVE_LOW>;
};

提示：Overlay 文件放在应用目录下，文件名为 boards/<BOARD_ID>.overlay，构建时 Zephyr 会自动加载它。也可以通过 -DDTC_OVERLAY_FILE=my_custom.overlay 指定自定义路径。

构建输出与烧录

构建输出文件

构建完成后，在 build/zephyr/ 目录下会生成以下关键文件：

文件格式用途
zephyr.elfELF包含调试信息的完整可执行文件，用于 GDB 调试
zephyr.bin纯二进制去除所有元数据的纯固件数据，用于直接烧录 Flash
zephyr.hexIntel HEX带地址信息的十六进制格式，大多数烧录工具的首选格式
zephyr.map链接器映射显示每个函数和变量的内存地址，用于分析内存使用

west flash 烧录命令

bash 
# 基本烧录（自动检测连接的开发板）
west flash

# 指定烧录器（runner）
west flash --runner jlink

west flash --runner openocd

west flash --runner pyocd

# 烧录指定 HEX 文件
west flash --hex-file build/zephyr/zephyr.hex

# 擦除整个 Flash 后再烧录
west flash --erase

# 指定 J-Link 的序列号（多调试器时有用）
west flash --runner jlink --dev-id 12345678

调试 — west debug

bash 
# 启动 GDB 调试会话
west debug

# 指定调试器
west debug --runner jlink

# 只启动 GDB Server（不连接客户端）
west debug --runner openocd --server-only

调试流程说明：

  1. west debug 会启动 GDB 客户端并连接到目标芯片
  2. 在 GDB 中使用 break main 设置断点
  3. 使用 continue 运行程序
  4. 使用 step、next、print 等命令进行调试

常见烧录问题

❌ 找不到调试器

确保调试器驱动已安装。J-Link 需要安装 SEGGER 驱动，OpenOCD 需要确保 USB 设备被识别。运行 west flash --runner jlink --verbose 查看详细日志。

❌ 烧录后程序不运行

检查以下可能原因：1) 设备树中 UART 或其他外设的引脚配置错误；2) Kconfig 中缺少必要的驱动配置；3) 供电不足导致芯片复位。查看串口输出是否有启动日志。

❌ Flash 空间不足

运行 west build -t rom_report 查看各模块占用的 Flash 空间。关闭不需要的 Kconfig 选项（如 CONFIG_LOG=n、CONFIG_DEBUG=n）可以显著减小固件体积。

💡 实用技巧

使用 west build -t ram_report 和 west build -t rom_report 可以分别查看 RAM 和 Flash 的详细使用情况，帮助你优化资源占用。如果需要更详细的分析，可以使用 west build -t puncover 生成可视化的代码大小分析报告。
