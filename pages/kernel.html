内核核心

深入理解 Zephyr RTOS 内核的核心机制 —— 线程、调度、同步、通信、中断、定时器、内存管理与多核支持

线程 Thread

线程是 Zephyr 内核最基本的执行单元。你可以把线程想象成一个"工人"——每个工人有自己的工具箱（栈空间）、自己的任务清单（入口函数），以及自己的优先等级（优先级）。Zephyr 中的线程和 FreeRTOS 中的任务（Task）是同一个概念。

创建线程的两种方式

Zephyr 提供了两种创建线程的方式：静态定义和动态创建。静态定义在编译期就分配好所有资源，动态创建则在运行时从堆上分配栈空间。

C 
/* 方式一：静态定义（编译期分配，推荐） */
K_THREAD_DEFINE(my_thread,       /* 线程名 */
                 512,              /* 栈大小（字节） */
                 my_thread_entry,   /* 入口函数 */
                 NULL, NULL, NULL,  /* arg1, arg2, arg3 */
                 5,                 /* 优先级 */
                 0,                 /* 选项 */
                 0);                /* 延迟启动(ms)，0=立即 */

/* 方式二：动态创建（运行时分配） */
struct k_thread my_thread_data;
k_tid_t my_tid;

K_THREAD_STACK_DEFINE(my_stack, 512);

my_tid = k_thread_create(&my_thread_data, my_stack,
                       K_THREAD_STACK_SIZEOF(my_stack),
                       my_thread_entry,
                       NULL, NULL, NULL,
                       5, 0, K_NO_WAIT);

/* 线程入口函数 */
void my_thread_entry(void *arg1, void *arg2, void *arg3)
{
    while (1) {
        printk("线程运行中...\n");
        k_msleep(1000);
    }
}

线程优先级

Zephyr 的线程优先级是一个非负整数，数值越小优先级越高。这一点和 FreeRTOS 相同，但和 Linux 恰好相反！

  • 优先级 0：最高优先级，属于协作式线程（Cooperative）
  • 优先级 0 ~ CONFIG_COOP_PRIORITIES-1：协作式线程区域
  • 优先级 CONFIG_COOP_PRIORITIES ~ 最低：抢占式线程区域（Preemptive）

小贴士：协作式线程运行时不会被其他线程抢占，必须主动让出 CPU（调用 k_yield()、k_sleep() 等阻塞函数）。抢占式线程则可以被更高优先级的线程随时打断。协作式线程适合执行关键的、不可被打断的逻辑。

线程生命周期管理

  • k_thread_start() — 启动一个被延迟创建的线程
  • k_thread_abort() — 终止一个线程（线程立即停止，资源不回收）
  • k_thread_join() — 等待一个线程结束（阻塞调用者）
  • k_yield() — 当前线程主动让出 CPU，让同优先级的其他线程运行
  • k_sleep(K_MSEC(100)) — 当前线程休眠指定时间
  • k_wakeup(tid) — 唤醒一个正在休眠的线程

注意：线程栈大小需要仔细斟酌。太小会导致栈溢出（难以调试的崩溃），太大则浪费宝贵的 RAM。可以通过 CONFIG_STACK_GROWS_UP 和栈分析工具 stackanalyze 来辅助判断。

调度器

调度器是内核的"交通指挥员"，它决定哪个线程在什么时候获得 CPU 的使用权。Zephyr 采用基于优先级的抢占式调度作为默认策略，同时支持协作式调度和时间片轮转。

调度规则

调度器的核心规则非常简单：

  1. 最高优先级的就绪线程总是先运行——没有例外
  2. 同优先级的就绪线程按时间片轮转（如果开启了时间片）
  3. 协作式线程运行期间不会被同优先级或更低优先级的线程抢占
  4. 抢占式线程可以被任何更高优先级的就绪线程抢占
调度触发时机

调度器并不是一直在"巡视"的，它只在以下时刻才会重新评估谁该运行：

  • 线程主动让出 CPU：k_yield()、k_sleep()、k_sem_take() 等阻塞操作
  • 中断服务程序（ISR）退出时
  • 线程调用了可能解锁更高优先级线程的操作，如 k_sem_give()、k_mutex_unlock()
  • 时间片定时器中断触发（如果开启了时间片）

时间片轮转

当多个同优先级的抢占式线程同时就绪时，可以通过时间片轮转让它们公平地分享 CPU 时间。通过配置项 CONFIG_TIMESLICING=y 开启，CONFIG_TIMESLICE_SIZE 设置时间片长度（毫秒），CONFIG_TIMESLICE_PRIORITY 设置参与时间片的最低优先级。

小贴士：协作式线程不参与时间片轮转。如果一个协作式线程不让出 CPU，同优先级的其他线程就永远得不到运行机会。所以协作式线程的代码要尽量短小精悍，及时调用 k_yield()。

线程间同步

多个线程协同工作时，需要同步机制来协调执行顺序、保护共享资源。Zephyr 提供了三种核心同步原语：信号量、互斥量和条件变量。

信号量 k_sem

信号量就像前台接待处的钥匙——前台有 N 把钥匙，每个来访者拿一把进入房间，钥匙用完了后来的来访者就得排队等待。有人归还钥匙，排队的人就能拿到钥匙进入。

  • 二值信号量（计数上限为 1）：只有一把钥匙，适合简单的"占用/释放"场景
  • 计数信号量（计数上限 > 1）：多把钥匙，适合资源池管理
C 
struct k_sem my_sem;

/* 初始化：初始计数 0，上限 1（二值信号量） */
k_sem_init(&my_sem, 0, 1);

/* 线程 A：等待信号量（阻塞直到有人 give） */
k_sem_take(&my_sem, K_FOREVER);

/* 线程 B / ISR：释放信号量 */
k_sem_give(&my_sem);

互斥量 k_mutex

互斥量就像会议室的门锁——谁先锁上门谁就独占会议室，其他人必须等他开锁出来后才能进入。和信号量不同，互斥量强调所有权：只有锁的持有者才能解锁。

互斥量最重要的特性是优先级继承（Priority Inheritance）：当低优先级线程持有锁，高优先级线程在等锁时，低优先级线程会临时"继承"高优先级，避免优先级反转问题。

C 
struct k_mutex my_mutex;

k_mutex_init(&my_mutex);

/* 加锁 — 获得独占访问权 */
k_mutex_lock(&my_mutex, K_FOREVER);

/* 临界区：安全地操作共享资源 */
shared_counter++;

/* 解锁 — 释放独占访问权 */
k_mutex_unlock(&my_mutex);

重要：不要在 ISR 中使用互斥量！ISR 不能阻塞等待，而 k_mutex_lock() 可能阻塞。信号量则可以在 ISR 中使用 k_sem_give()。

条件变量 k_condvar

条件变量就像医院的叫号系统——病人在等候区等待叫号（k_condvar_wait()），医生看完一个病人后按下叫号器（k_condvar_signal()），通知下一个病人进来。如果一次叫所有等候的病人，那就是 k_condvar_broadcast()。

条件变量必须和互斥量配合使用：等待时自动释放互斥量，被唤醒时重新获取互斥量。

C 
struct k_mutex data_mutex;
struct k_condvar data_condvar;
bool data_ready = false;

/* 消费者线程：等待数据就绪 */
k_mutex_lock(&data_mutex, K_FOREVER);
while (!data_ready) {
    k_condvar_wait(&data_condvar, &data_mutex, K_FOREVER);
}
/* 数据已就绪，处理数据 */
process_data();
k_mutex_unlock(&data_mutex);

/* 生产者线程：产生数据后通知 */
k_mutex_lock(&data_mutex, K_FOREVER);
produce_data();
data_ready = true;
k_condvar_signal(&data_condvar);
k_mutex_unlock(&data_mutex);

线程间通信

同步解决的是"谁先谁后"的问题，通信解决的是"传递数据"的问题。Zephyr 提供了三种 IPC 机制：消息队列、管道和邮箱。

消息队列 k_msgq

消息队列就像公司的信箱——每个人往信箱里投信（k_msgq_put()），收信人从信箱取信（k_msgq_get()）。每封信的大小是固定的，信箱容量也是固定的。信箱满了再投信就得排队，信箱空了取信也得等待。

C 
struct k_msgq my_msgq;

/* 定义消息结构（固定大小） */
struct sensor_data {
    int temperature;
    int humidity;
};

/* 初始化消息队列：最多 8 条消息 */
K_MSGQ_DEFINE(my_msgq, sizeof(struct sensor_data), 8, 4);

/* 发送端 */
struct sensor_data data = {
    .temperature = 25,
    .humidity = 60
};
k_msgq_put(&my_msgq, &data, K_NO_WAIT);

/* 接收端 */
struct sensor_data received;
k_msgq_get(&my_msgq, &received, K_FOREVER);
printk("温度: %d, 湿度: %d\n", received.temperature, received.humidity);

管道 k_pipe

管道就像水管——数据像水一样从一端流入，从另一端流出。和消息队列不同，管道传输的是字节流，没有消息边界。一次可以写入或读取任意长度的数据，适合流式数据传输。

  • k_pipe_put() — 向管道写入数据
  • k_pipe_get() — 从管道读取数据
  • 支持部分读写：一次操作可能只传输了部分数据

邮箱 k_mbox

邮箱是增强版的消息队列，支持同步和异步两种发送方式，消息可以携带可选的发送者信息，接收者可以选择性地接收特定发送者的消息。适合需要更灵活消息路由的场景。

特性 k_msgq 消息队列 k_pipe 管道 k_mbox 邮箱
数据格式 固定大小消息 字节流 变长消息 + 元数据
消息边界 有 无 有
发送方式 同步 同步 同步 + 异步
适用场景 结构化数据传递 流式数据传输 灵活消息路由

中断管理

中断是嵌入式系统的"紧急电话"——当外部事件发生时（按键按下、数据到达、定时器到期），硬件会打断当前正在执行的代码，跳转到中断服务程序（ISR）进行处理。中断的优先级高于任何线程。

ISR 基础

ISR（Interrupt Service Routine）是中断发生时执行的函数。ISR 的核心原则是快进快出——在 ISR 中只做最紧急的处理，耗时操作推迟到线程中完成。这就像急诊分诊：ISR 只做止血包扎，手术交给手术室（线程）。

C 
/* 定义 ISR */
void my_isr(const void *device)
{
    /* 只做最紧急的操作 */
    uint32_t status = read_status_reg();

    if (status & RX_READY) {
        /* 读取数据，提交延迟处理 */
        k_work_submit(&rx_work);
    }
}

/* 连接中断：将 IRQ 23 绑定到 my_isr */
IRQ_CONNECT(23,            /* IRQ 编号 */
             0,              /* 中断优先级 */
             my_isr,          /* ISR 函数 */
             NULL,            /* ISR 参数 */
             0);             /* flags */

/* 使能中断 */
irq_enable(23);

中断优先级

中断优先级和线程优先级是两个独立的体系。数值越小，中断优先级越高（和线程优先级方向一致）。高优先级中断可以抢占低优先级中断，形成中断嵌套。通过 CONFIG_IRQ_OFFLOAD 可以将中断处理卸载到线程上下文。

延迟处理模式（Bottom-Half）

中断处理分为"上半部"（Top-Half）和"下半部"（Bottom-Half）：

  • 上半部（ISR 中）：关中断状态下执行，只做最紧急的硬件操作（读取数据、清除标志、提交工作）
  • 下半部（线程中）：开中断状态下执行，做耗时的数据处理、协议解析等

Zephyr 中实现下半部的标准方式就是工作队列（见下文 #workqueue 章节）。

ISR 中的限制：ISR 中不能调用任何可能阻塞的内核 API（如 k_mutex_lock()、k_msgq_get() 带 K_FOREVER），不能使用 k_sleep()，不能分配内存。可以使用 k_sem_give()、k_work_submit()、k_msgq_put() 带 K_NO_WAIT 等非阻塞 API。

定时器

定时器是嵌入式开发的"闹钟"——你需要定时执行某个操作、周期性检查某个状态、或者测量时间间隔，都离不开定时器。Zephyr 提供了系统时钟、内核定时器和多种等待/延时 API。

系统时钟

Zephyr 内核维护一个系统时钟（System Clock），通过 k_uptime_get() 获取自系统启动以来的微秒数。这是所有时间相关功能的基础。

k_timer 内核定时器

k_timer 是内核提供的高层定时器，支持单次触发和周期触发。你可以把它想象成一个可编程闹钟——设定好时间后，到点就会调用你的回调函数。

C 
struct k_timer my_timer;
volatile int timer_count = 0;

/* 定时器到期回调（在 ISR 上下文中执行！）*/
void timer_expiry_fn(struct k_timer *timer)
{
    timer_count++;
}

/* 定时器停止回调（在线程上下文中执行）*/
void timer_stop_fn(struct k_timer *timer)
{
    printk("定时器已停止，共触发 %d 次\n", timer_count);
}

/* 初始化并启动定时器 */
k_timer_init(&my_timer, timer_expiry_fn, timer_stop_fn);
k_timer_start(&my_timer, K_MSEC(100),   /* 首次到期时间 */
                        K_MSEC(500));   /* 周期时间 */

/* 查询定时器已触发次数 */
uint32_t count = k_timer_status_get(&my_timer);

/* 停止定时器 */
k_timer_stop(&my_timer);

延时与等待 API

API 说明 上下文
k_msleep(ms) 休眠指定毫秒，让出 CPU 线程
k_usleep(us) 休眠指定微秒，让出 CPU 线程
k_sleep(timeout) 通用休眠，接受 K_MSEC/K_SECONDS 等 线程
k_busy_wait(us) 忙等待（死循环），不让出 CPU 线程/ISR
k_yield() 让出 CPU，让同优先级线程运行 线程

超时模式

Zephyr 中几乎所有阻塞 API 都接受一个超时参数，常用的超时宏有：

  • K_FOREVER — 永远等待，直到操作完成
  • K_NO_WAIT — 不等待，立即返回（非阻塞）
  • K_MSEC(n) — 等待最多 n 毫秒
  • K_SECONDS(n) — 等待最多 n 秒
  • K_MINUTES(n) — 等待最多 n 分钟
  • K_HOURS(n) — 等待最多 n 小时

内存管理

嵌入式系统的内存是稀缺资源，Zephyr 提供了多种内存管理方案来满足不同场景的需求。选择合适的内存管理策略，就像选择合适的收纳方式——固定大小的格子用抽屉（k_mem_slab），不规则大小的东西用储物箱（k_heap）。

k_heap 堆内存

k_heap 提供类似 malloc/free 的变长内存分配，适合分配大小不确定的内存块。每个 k_heap 有自己独立的堆区域，避免了全局堆的碎片化问题。

k_mem_slab 内存块分配器

k_mem_slab 就像一个冰格——所有格子大小完全一样，每个格子只能装固定大小的东西。分配和释放都是 O(1) 操作，不会产生内存碎片，非常适合分配固定大小的控制块、缓冲区等。

C 
/* k_heap 示例 */
struct k_heap my_heap;
K_HEAP_DEFINE(my_heap, 4096);  /* 4KB 堆空间 */

void *ptr = k_heap_alloc(&my_heap, 128, K_FOREVER);
if (ptr != NULL) {
    memset(ptr, 0, 128);
    /* 使用内存... */
    k_heap_free(&my_heap, ptr);
}

/* k_mem_slab 示例 */
struct k_mem_slab my_slab;

K_MEM_SLAB_DEFINE(my_slab,     /* 名称 */
                   64,          /* 每个块大小 */
                   16,          /* 块数量 */
                   4);          /* 对齐字节数 */

void *block;
if (k_mem_slab_alloc(&my_slab, &block, K_NO_WAIT) == 0) {
    /* 成功获取一个 64 字节的块 */
    k_mem_slab_free(&my_slab, block);
}

内存保护

在支持 MPU（Memory Protection Unit）或 MMU（Memory Management Unit）的硬件上，Zephyr 可以实现内存保护：

  • 栈溢出检测：通过 CONFIG_STACK_CANARIES 在栈底放置哨兵值，检测栈溢出
  • MPU 内存保护：通过 CONFIG_MEMORY_PROTECTION 开启，防止线程越界访问
  • 用户模式隔离：通过 CONFIG_USERSPACE 开启，用户态线程只能访问自己的内存区域，内核空间完全隔离

注意：k_mem_pool 已在 Zephyr 3.5 中废弃，请使用 k_heap 替代。栈对齐要求通常为 4 字节或 8 字节，使用 K_THREAD_STACK_DEFINE 宏可以自动处理对齐。

工作队列

工作队列是中断下半部处理的标准方案。你可以把工作队列想象成一个待办事项清单——ISR 只需往清单上贴一张便签（提交工作），然后立刻返回。工作线程会按照清单逐个处理这些事项，处理过程在线程上下文中执行，可以使用所有内核 API。

为什么用工作队列而不是直接在 ISR 中处理？

  • ISR 执行期间会屏蔽其他中断，长时间 ISR 会影响系统实时性
  • ISR 中不能使用阻塞 API（互斥量、信号量等待等）
  • 工作队列在线程上下文执行，可以使用完整的内核 API
  • 工作队列自动管理调度，无需手动创建线程
C 
/* 定义工作项 */
struct k_work rx_work;

/* 工作处理函数（在线程上下文执行）*/
void rx_work_handler(struct k_work *work)
{
    /* 可以安全地使用阻塞 API */
    k_mutex_lock(&data_mutex, K_FOREVER);
    process_rx_data();
    k_mutex_unlock(&data_mutex);
}

/* 初始化工作项 */
k_work_init(&rx_work, rx_work_handler);

/* 在 ISR 中提交工作到系统工作队列 */
void uart_isr(const void *dev)
{
    /* 快速读取硬件数据 */
    read_hw_fifo();
    /* 提交延迟处理，立即返回 */
    k_work_submit(&rx_work);
}

/* 延迟工作：5 秒后执行 */
struct k_delayed_work periodic_work;
k_delayed_work_init(&periodic_work, periodic_handler);
k_delayed_work_submit(&periodic_work, K_SECONDS(5));

系统工作队列 vs 自定义工作队列

Zephyr 提供一个默认的系统工作队列（k_sys_work_q），优先级为 CONFIG_SYSTEM_WORKQUEUE_PRIORITY（默认 -1 即较高优先级）。大多数场景直接使用系统工作队列即可。如果需要不同优先级或隔离处理，可以创建自定义工作队列：

C 
K_THREAD_STACK_DEFINE(my_work_q_stack, 1024);
struct k_work_queue my_work_q;

k_work_queue_start(&my_work_q, my_work_q_stack,
                     K_THREAD_STACK_SIZEOF(my_work_q_stack),
                     7, /* 优先级 */
                     NULL);

/* 提交到自定义工作队列 */
k_work_submit_to_queue(&my_work_q, &rx_work);

SMP 多核支持

随着多核 MCU 的普及（如 NXP i.MX RT1170、ESP32 双核），Zephyr 也提供了 SMP（Symmetric Multi-Processing）支持，让多个 CPU 核心可以同时运行不同的线程。

启用 SMP

通过配置项 CONFIG_SMP=y 启用 SMP 支持，CONFIG_MP_MAX_NUM_CPUS 设置最大 CPU 核心数。启用后，调度器会自动在多个核心间分配线程。

线程亲和性

默认情况下，线程可以在任何 CPU 核心上运行。但有时你需要将线程"钉"在某个核心上——比如让中断处理线程固定在处理该中断的 CPU 上。这时可以使用线程亲和性 API：

  • k_thread_cpu_pin(tid, cpu_id) — 将线程固定到指定 CPU
  • k_thread_cpu_mask_clear(tid) — 清除所有 CPU 亲和性
  • k_thread_cpu_mask_enable(tid, cpu_id) — 允许线程在指定 CPU 运行

负载均衡

Zephyr 的 SMP 调度器会自动进行负载均衡：当一个 CPU 上的线程全部阻塞时，调度器会从其他 CPU 的就绪队列中"拉"线程过来执行。这种工作窃取（Work Stealing）策略确保了多核利用率。

Per-CPU 数据

在 SMP 系统中，每个 CPU 核心都有自己的私有数据，如当前线程指针、中断嵌套计数等。Zephyr 通过 CONFIG_SMP 自动处理 per-CPU 数据的隔离，开发者通常不需要关心这些细节。

何时使用 SMP？并非所有场景都适合 SMP。如果你的应用对实时性要求极高，SMP 带来的锁竞争和缓存一致性开销可能反而降低性能。SMP 最适合的场景是：多个独立的、可并行执行的任务（如一个核跑通信协议栈，另一个核跑传感器采集和算法处理）。对于简单的单任务场景，单核配置更高效。

内核核心知识速查

线程是执行单元，调度器是交通指挥，信号量是前台钥匙，互斥量是会议室门锁，消息队列是信箱，工作队列是待办清单——理解了这些类比，你就掌握了 Zephyr 内核的核心设计思想！
