网络与通信

全面掌握 Zephyr RTOS 的网络能力 —— 从协议栈架构到 Wi-Fi、BLE、MQTT、CoAP、HTTP、LoRaWAN、Thread、Socket 编程与网络安全

网络协议栈架构

Zephyr 的网络协议栈采用分层架构设计，就像一个邮政系统：你写好信（应用数据），装进信封（TCP/UDP），贴上地址标签（IP），交给邮局（L2 链路层），邮局通过公路/铁路（物理介质）把信送到目的地。每一层只关心自己的职责，不需要了解上下的细节。

协议栈层次

Text 
┌─────────────────────────────────────┐
│          应用层 (Application)         │  HTTP / MQTT / CoAP / DNS
├─────────────────────────────────────┤
│         传输层 (Transport)           │  TCP / UDP
├─────────────────────────────────────┤
│          网络层 (Network)            │  IPv4 / IPv6 / ICMP
├─────────────────────────────────────┤
│        链路层 (L2 / Link)            │  Ethernet / IEEE 802.15.4 / BLE
├─────────────────────────────────────┤
│         物理层 (Physical)            │  硬件驱动
└─────────────────────────────────────┘

核心数据结构

  • net_if — 网络接口，相当于"网卡"。每个网络接口对应一个物理或虚拟的网络设备，拥有自己的 IP 地址、MAC 地址和 MTU。一个设备可以同时拥有多个 net_if（比如同时有 Wi-Fi 和以太网）。
  • net_pkt — 网络数据包，相当于"信件"。它是协议栈中数据传递的基本单位，包含了从 L2 到应用层的所有数据。net_pkt 内部使用 net_buf 链表来管理分散的内存片段，避免数据拷贝。
  • net_context — 网络上下文，相当于"通信管道"。它封装了一个网络连接的所有状态信息（socket 地址、协议类型、回调函数等），是应用层与协议栈交互的桥梁。

小贴士：Zephyr 的网络协议栈默认使用 IPv6，同时也支持 IPv4 和双栈（IPv4/IPv6）模式。对于资源受限的 IoT 设备，推荐使用 IPv6 + 6LoWPAN 压缩，可以显著减少无线传输的开销。

Wi-Fi 连接管理

Wi-Fi 是最常见的物联网联网方式。Zephyr 通过 net_mgmt（网络管理框架）来处理 Wi-Fi 事件，提供了一套统一的 API 来完成扫描、连接、断开等操作。你可以把 net_mgmt 想象成"Wi-Fi 的广播站"——它会在连接成功、断开、信号变化时广播通知，你的应用只需要"收听"这些通知即可。

Wi-Fi 连接流程

C 
static struct net_mgmt_event_callback mgmt_cb;

static void wifi_mgmt_event_handler(struct net_mgmt_event_callback *cb,
                                     uint32_t mgmt_event, struct net_if *iface)
{
    switch (mgmt_event) {
    case NET_EVENT_WIFI_CONNECT_RESULT:
        printk("Wi-Fi 已连接！\n");
        break;
    case NET_EVENT_WIFI_DISCONNECT_RESULT:
        printk("Wi-Fi 已断开！\n");
        break;
    default:
        break;
    }
}

static int wifi_connect(void)
{
    struct net_if *iface = net_if_get_default();
    struct wifi_connect_req_params params = {
        .ssid = "MyHomeWiFi",
        .ssid_length = 10,
        .psk = "password123",
        .psk_length = 11,
        .security = WIFI_SECURITY_TYPE_PSK,
        .channel = WIFI_CHANNEL_ANY,
    };

    net_mgmt_init_event_callback(&mgmt_cb, wifi_mgmt_event_handler,
                                     NET_EVENT_WIFI_CONNECT_RESULT |
                                     NET_EVENT_WIFI_DISCONNECT_RESULT);
    net_mgmt_add_event_callback(&mgmt_cb);

    if (net_mgmt(NET_REQUEST_WIFI_CONNECT, iface,
                  &params, sizeof(params))) {
        printk("Wi-Fi 连接请求失败\n");
        return -1;
    }

    return 0;
}

Wi-Fi 扫描

连接之前通常需要先扫描周围的 AP，获取可用的 SSID 列表和信号强度。通过 NET_REQUEST_WIFI_SCAN 发起扫描请求，扫描结果通过 NET_EVENT_WIFI_SCAN_RESULT 事件逐个返回。

注意：Wi-Fi 连接是异步操作。调用 net_mgmt(NET_REQUEST_WIFI_CONNECT, ...) 只是发起连接请求，实际连接结果需要通过事件回调获知。不要在发起连接后立即发送网络数据，一定要等到 NET_EVENT_WIFI_CONNECT_RESULT 事件。

蓝牙低功耗 BLE

BLE（Bluetooth Low Energy）是 IoT 领域最流行的短距离通信协议之一。Zephyr 拥有业界最完善的开源 BLE 协议栈实现。理解 BLE 的关键在于两个概念：GAP（通用访问规范）和 GATT（通用属性规范）。

GAP：角色与广播

GAP 定义了设备如何"发现"彼此和建立连接。BLE 广播就像在大街上喊出自己的手机号——你不停地广播自己的信息，感兴趣的人（扫描者）听到后就可以主动联系你。GAP 定义了四种角色：

  • 外设（Peripheral）：广播自己，等待被连接（如心率手环）
  • 中心（Central）：扫描并主动发起连接（如手机）
  • 广播者（Broadcaster）：只广播，不可连接（如信标 Beacon）
  • 观察者（Observer）：只扫描，不连接（如温度采集器）

GATT：服务与特征

GATT 定义了连接后数据如何组织。你可以把 GATT 想象成餐厅的菜单——菜单（Service）下面有多个菜品（Characteristic），每个菜品有名称（UUID）、口味描述（Descriptor）和价格（Value）。客户端可以点菜（Read）、改口味（Write）或者订阅新菜通知（Notify/Indicate）。

  • 服务（Service）：一组相关特征的集合，用 UUID 标识
  • 特征（Characteristic）：实际的数据项，包含值和属性（可读/可写/可通知）
  • 描述符（Descriptor）：特征的元数据，如 CCCD（客户端特征配置描述符）用于开关通知

小贴士：BLE 数据包最大载荷只有 20 字节（默认 MTU）。如果需要传输更多数据，可以协商更大的 MTU（bt_gatt_exchange_mtu()），或使用 L2CAP 面向连接通道。Zephyr 3.x 默认支持扩展广播和 PHY 2M，可以显著提高吞吐量。

MQTT 协议客户端

MQTT 是物联网领域最广泛使用的应用层协议。你可以把 MQTT 想象成报纸订阅系统——出版社（发布者）把报纸投递到报社（Broker），报社根据订阅名单把报纸分发给各个订户（订阅者）。发布者和订阅者互不认识，完全通过 Broker 中转，这就是经典的发布/订阅模式。

QoS 服务等级

QoS 等级 说明 可靠性 开销
QoS 0 至多一次（发完即忘） 最低，可能丢失 最小
QoS 1 至少一次（需确认） 较高，可能重复 中等
QoS 2 恰好一次（四次握手） 最高，不丢不重 最大

MQTT 发布温度数据

C 
static struct mqtt_client client;
static uint8_t rx_buffer[256];
static uint8_t tx_buffer[256];

static void mqtt_evt_handler(struct mqtt_client *cli,
                                const struct mqtt_evt *evt)
{
    switch (evt->type) {
    case MQTT_EVT_CONNACK:
        printk("MQTT 连接成功！\n");
        break;
    case MQTT_EVT_PUBLISH:
        printk("收到订阅消息\n");
        break;
    case MQTT_EVT_DISCONNECT:
        printk("MQTT 已断开\n");
        break;
    default:
        break;
    }
}

static int mqtt_publish_temp(float temperature)
{
    struct mqtt_publish_param pub = {
        .message.topic.topic = {
            .utf8 = "sensors/temperature",
            .size = sizeof("sensors/temperature") - 1,
        },
        .message.topic.qos = MQTT_QOS_1_AT_LEAST_ONCE,
        .message.payload.data = NULL,
        .message.payload.len = 0,
        .message_id = sys_rand16_get(),
    };

    char payload[32];
    int len = snprintf(payload, sizeof(payload),
                         "{\"temp\":%.1f}", temperature);
    pub.message.payload.data = payload;
    pub.message.payload.len = len;

    return mqtt_publish(&client, &pub);
}

static int mqtt_connect_to_broker(void)
{
    mqtt_client_init(&client);

    struct sockaddr_in broker = {
        .sin_family = AF_INET,
        .sin_port = htons(1883),
    };
    zsock_inet_pton(AF_INET, "192.168.1.100", &broker.sin_addr);

    mqtt_client_set_broker(&client, sizeof(broker));
    client.broker = (struct sockaddr *)&broker;
    client.evt_cb = mqtt_evt_handler;
    client.client_id.utf8 = "zephyr_sensor";
    client.client_id.size = sizeof("zephyr_sensor") - 1;
    client.rx_buf = rx_buffer;
    client.rx_buf_size = sizeof(rx_buffer);
    client.tx_buf = tx_buffer;
    client.tx_buf_size = sizeof(tx_buffer);

    return mqtt_connect(&client);
}

注意：MQTT 客户端需要应用层定期调用 mqtt_input() 处理接收数据和 mqtt_live() 维持心跳。通常的做法是在一个独立线程中循环调用这两个函数，或者使用 poll() 监听 socket 可读事件后再调用。

CoAP 协议

CoAP（Constrained Application Protocol）是专为资源受限设备设计的 Web 协议。你可以把 CoAP 理解为"轻量版 HTTP"——它同样使用 RESTful 风格（GET/PUT/POST/DELETE），但运行在 UDP 而非 TCP 之上，报文头仅 4 字节（HTTP 头动辄数百字节），非常适合电池供电的 IoT 设备。

CoAP 核心特性

  • RESTful 方法：GET（读取）、POST（创建/触发）、PUT（更新）、DELETE（删除）
  • 观察模式（Observe）：类似 MQTT 的订阅，客户端可以"观察"一个资源，服务端在资源变化时主动推送通知
  • 确认/非确认消息：CON（需要确认）和 NON（不需要确认），灵活权衡可靠性与开销
  • 块传输：支持分块传输大数据，不需要一次性装进小数据包

CoAP GET 请求示例

C 
static int coap_get_request(void)
{
    struct coap_packet request;
    struct coap_packet response;
    const uint8_t *payload;
    uint16_t payload_len;
    uint8_t token[8];
    uint8_t token_len = 2;

    coap_packet_init(&request, COAP_VERSION,
                      COAP_TYPE_CON, 8,
                      COAP_METHOD_GET,
                      token, token_len,
                      coap_next_id());

    coap_packet_append_option(&request, COAP_OPTION_URI_PATH,
                               "sensors/temp",
                               sizeof("sensors/temp") - 1);

    /* 发送请求并等待响应 */
    coap_send_request(&request, &remote_addr);

    /* 接收响应 */
    coap_receive(&response);
    payload = coap_packet_get_payload(&response, &payload_len);
    printk("温度: %.*s\n", payload_len, payload);

    return 0;
}

小贴士：CoAP 默认端口是 5683（UDP），DTLS 加密端口是 5684。在公网部署时务必启用 DTLS，否则数据明文传输非常不安全。

HTTP 客户端/服务端

HTTP 是互联网最基础的协议，Zephyr 同时提供了 HTTP 客户端和服务端实现。HTTP 客户端用于设备向云端上报数据或调用 REST API，HTTP 服务端则让设备本身成为一个可被访问的 Web 服务。

HTTP 客户端 GET 请求

C 
static uint8_t recv_buf[1024];

static void http_response_cb(struct http_response *resp,
                              enum http_final_call final_data,
                              void *user_data)
{
    printk("HTTP 状态码: %d\n", resp->http_status);
    printk("响应体: %.*s\n", resp->body_frag_len, resp->body_frag_start);
}

static int http_get_request(void)
{
    struct http_request req = {
        .method = HTTP_GET,
        .url = "/api/v1/temperature",
        .host = "weather.example.com",
        .protocol = "HTTP/1.1",
    };

    struct http_client_ctx ctx = {
        .recv_buf = recv_buf,
        .recv_buf_len = sizeof(recv_buf),
    };

    return http_client_req(&ctx, &req, 5000, http_response_cb);
}

HTTP 服务端

Zephyr 的 HTTP 服务端支持 REST API 路由，可以为设备提供配置页面或数据接口。通过 http_server_add_url() 注册 URL 路径和回调函数，支持 GET、POST、PUT、DELETE 等方法。适合在局域网内对设备进行 Web 管理的场景。

注意：HTTP 基于 TCP，开销较大。对于带宽受限或电池供电的设备，优先考虑 CoAP 或 MQTT。HTTP 更适合有稳定电源和充足带宽的网关类设备。

LoRaWAN 通信

LoRaWAN 是一种远距离、低功耗的广域网通信技术，传输距离可达数公里，非常适合智能农业、智慧城市等场景。你可以把 LoRaWAN 想象成"大喇叭广播"——你用很小的力气喊一声，方圆几公里都能听到，但每次只能喊很短的内容。

LoRaWAN 设备类别

类别 上行 下行 功耗 适用场景
Class A 任意时刻 仅在上行后短暂窗口 最低 传感器上报（最常用）
Class B 任意时刻 定时信标窗口 中等 需要定时下行的场景
Class C 任意时刻 持续监听 最高 常供电的网关/执行器

{
    const struct device *lora_dev = DEVICE_DT_GET(DT_ALIAS(lora0));
    struct lorawan_join_config join_cfg = {
        .dev_eui = { 0x01, 0x02, 0x03, 0x04,

        .app_eui = { 0x11, 0x22, 0x33, 0x44,

        .app_key = { 0xAA, 0xBB, 0xCC, 0xDD,
                     0xEE, 0xFF, 0x00, 0x11,
                     0x22, 0x33, 0x44, 0x55,
                     0x66, 0x77, 0x88, 0x99 },
    };

    lorawan_set_datarate(LORAWAN_DR_0);
    lorawan_set_adr(true);

        printk("入网失败！\n");

    }
    printk("入网成功！\n");

    return lorawan_send(data, sizeof(data), 2, false);
}

小贴士：LoRaWAN 有两种入网方式：OTAA（Over-The-Air Activation，空中激活）更安全，设备通过 AppKey 与网络服务器协商会话密钥；ABP（Activation By Personalization，预置激活）直接写入会话密钥，部署简单但安全性较低。生产环境推荐 OTAA。

Thread/OpenThread 网状网络

Thread 是一种基于 IEEE 802.15.4 的低功耗网状网络协议，由 Google Nest、Apple、Samsung 等巨头联合推动。你可以把 Thread 网络想象成"蚂蚁群落"——每只蚂蚁（节点）都能通过信息素（路由）找到食物（目标节点），即使某条路径断了，蚂蚁们也能自动找到新路径。这种自愈能力是网状网络最大的优势。

Thread 核心概念

  • IEEE 802.15.4：Thread 的物理层和 MAC 层标准，工作在 2.4GHz 或 Sub-GHz 频段，低功耗短距离通信
  • 网状拓扑：节点之间可以互相中继数据，扩大覆盖范围，单点故障不影响整个网络
  • Border Router：Thread 网络与 IP 网络（如 Wi-Fi/以太网）之间的桥梁，让 Thread 设备可以被互联网访问
  • OpenThread：Google 开源的 Thread 协议栈实现，Zephyr 已集成 OpenThread 作为其 Thread 协议栈

Thread 设备角色

  • Router：全功能路由节点，可以转发数据，维护路由表
  • End Device：终端设备，通过父节点（Router）通信，低功耗休眠
  • Sleepy End Device (SED)：休眠终端设备，大部分时间在休眠，定期唤醒接收数据
  • Border Router：边界路由器，连接 Thread 网络与外部 IP 网络

注意：Thread 和 Zigbee 都基于 IEEE 802.15.4，但 Thread 原生支持 IPv6（通过 6LoWPAN），而 Zigbee 使用自己的应用层协议。Thread 更适合需要与互联网无缝集成的 IoT 场景。Matter 协议（原 CHIP 项目）使用 Thread 作为低功耗设备的传输层。

Socket 编程接口

Zephyr 实现了POSIX 兼容的 BSD Socket API，让有 Linux 网络编程经验的开发者可以无缝迁移。所有 socket 函数都有 zsock_ 前缀版本（如 zsock_socket()、zsock_connect()），同时通过 CONFIG_POSIX_API 可以直接使用标准名称（socket()、connect() 等）。

Socket API 速查

函数 说明 对应 zsock_ 前缀
socket() 创建 socket zsock_socket()
bind() 绑定地址和端口 zsock_bind()
listen() 开始监听连接 zsock_listen()
accept() 接受新连接 zsock_accept()
connect() 发起连接 zsock_connect()
send() 发送数据 zsock_send()
recv() 接收数据 zsock_recv()
close() 关闭 socket zsock_close()
poll() 多路复用 I/O zsock_poll()

TCP 客户端示例

C 
static int tcp_client(void)
{
    int sock = zsock_socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);
    if (sock < 0) {
        printk("创建 socket 失败\n");
        return -1;
    }

    struct sockaddr_in server = {
        .sin_family = AF_INET,
        .sin_port = htons(8080),
    };
    zsock_inet_pton(AF_INET, "192.168.1.100", &server.sin_addr);

    if (zsock_connect(sock, (struct sockaddr *)&server,
                       sizeof(server)) < 0) {
        printk("连接服务器失败\n");
        zsock_close(sock);
        return -1;
    }

    const char *msg = "Hello from Zephyr!\n";
    zsock_send(sock, msg, strlen(msg), 0);

    char buf[128];
    ssize_t len = zsock_recv(sock, buf, sizeof(buf) - 1, 0);
    if (len > 0) {
        buf[len] = '\0';
        printk("收到: %s\n", buf);
    }

    zsock_close(sock);
    return 0;
}

小贴士：使用 zsock_poll() 可以同时监听多个 socket 的可读/可写事件，避免为每个连接创建独立线程。这是构建高性能网络服务（如多客户端 TCP 服务器）的推荐方式。

网络安全 TLS/DTLS

在物联网时代，网络安全不再是可选项而是必选项。Zephyr 集成了 mbedTLS 库，提供完整的 TLS/DTLS 支持，让你的设备通信固若金汤。

TLS vs DTLS

  • TLS（Transport Layer Security）：保护 TCP 连接，如 HTTPS、MQTT over TLS。TLS 1.2 是当前最广泛部署的版本，TLS 1.3 提供更快的握手和更强的安全性
  • DTLS（Datagram TLS）：保护 UDP 连接，如 CoAP over DTLS。DTLS 在 UDP 之上增加了重传和排序机制，确保加密握手可靠完成

证书管理

TLS/DTLS 的核心是证书体系。Zephyr 支持以下证书管理方式：

  • CA 证书：用于验证服务器身份，通常烧录到设备固件中
  • 设备证书/私钥：用于双向认证（mTLS），每个设备拥有唯一的证书和私钥
  • PSK（预共享密钥）：对称密钥方案，开销更小，适合资源受限设备

prj.conf 安全配置

Conf 
# 启用 TLS 支持
CONFIG_MBEDTLS=y
CONFIG_MBEDTLS_BUILTIN=y

# TLS 1.2（默认启用）
CONFIG_MBEDTLS_TLS_VERSION_1_2=y

# TLS 1.3（可选，更安全更快）
CONFIG_MBEDTLS_TLS_VERSION_1_3=y

# DTLS 支持（用于 CoAP 等 UDP 协议）
CONFIG_MBEDTLS_DTLS=y

# 启用证书验证
CONFIG_MBEDTLS_X509=y
CONFIG_MBEDTLS_CERTIFICATE_C=y

# 网络层 TLS 集成
CONFIG_NET_SOCKETS_TLS=y
CONFIG_NET_SOCKETS_TLS_MAX_CONTEXTS=4

# 内存优化：按需裁剪密码套件
CONFIG_MBEDTLS_CIPHER_AES_ENABLED=y
CONFIG_MBEDTLS_CIPHER_GCM_ENABLED=y
CONFIG_MBEDTLS_ECP_C=y
CONFIG_MBEDTLS_ECDHE_ENABLED=y

安全警告：切勿将私钥硬编码在源代码中！生产环境应使用安全存储（如 TrustZone、SE05X 等 HSM 模块）保护私钥。开发阶段可以使用 PSA Protected Storage 或 Kconfig 的 PEM 文件加载方式。
