高级特性

掌握 Zephyr RTOS 的高级能力 —— 电源管理、安全框架、OTA 升级、文件系统、Shell 调试、日志系统、持久化存储、用户空间、模块化与测试框架

电源管理

电源管理是嵌入式设备的"省电大师"——就像手机不用时会自动息屏、进入休眠一样，Zephyr 的电源管理子系统可以根据系统负载自动将 CPU 和外设切换到低功耗状态，从而延长电池寿命。

电源状态

Zephyr 定义了五种电源状态，功耗从高到低排列：

状态 说明 唤醒延迟 功耗
Active CPU 全速运行，所有外设可用 无 最高
Idle CPU 空闲，等待中断唤醒（WFI） 微秒级 低
Suspend CPU 停止，部分外设关闭，RAM 保留 毫秒级 较低
Standby 深度休眠，仅 RTC 和唤醒逻辑工作 秒级 极低
Off 系统完全断电，仅靠外部信号重启 重启时间 近乎零

自动空闲与运行时电源管理

当所有线程都处于阻塞状态时，Zephyr 的空闲线程会自动运行。如果启用了 CONFIG_PM，空闲线程会根据策略自动将系统切换到低功耗状态——这就像办公室没人时自动关灯一样自然。

pm_device_runtime 是设备级的运行时电源管理：当设备不被使用时自动挂起（suspend），需要使用时自动恢复（resume）。开发者只需调用 pm_device_runtime_get() 和 pm_device_runtime_put()，框架会自动处理状态切换。

C 
/* prj.conf 中启用电源管理 */
/* CONFIG_PM=y                  */
/* CONFIG_PM_DEVICE=y           */
/* CONFIG_PM_DEVICE_RUNTIME=y   */

const struct device *sensor = DEVICE_DT_GET(DT_NODELABEL(my_sensor));

/* 使用设备前：请求恢复（自动从低功耗唤醒）*/
pm_device_runtime_get(sensor);

/* 读取传感器数据 */
struct sensor_value val;
sensor_sample_fetch(sensor);
sensor_channel_get(sensor, SENSOR_CHAN_TEMPERATURE, &val);

/* 使用完毕：释放设备（自动进入低功耗）*/
pm_device_runtime_put(sensor);

注意：电源状态切换有延迟代价。进入 Standby 越深，唤醒越慢。如果你的应用对实时响应要求很高（如电机控制），需要仔细权衡功耗与延迟。可以通过 CONFIG_PM_POLICY_LATENCY 设置可接受的最大延迟，让 PM 策略自动选择最深的合适状态。

安全框架

在物联网时代，安全不再是"锦上添花"，而是"必备基础设施"。Zephyr 的安全框架就像一栋大厦的安保系统——有门禁（安全启动）、有保险柜（加密存储）、有加密电话（TLS 通信），层层防护确保设备不被篡改、数据不被窃取。

mbedTLS 与 PSA Crypto API

Zephyr 集成了 mbedTLS 作为底层加密库，提供 AES、RSA、ECC、SHA、HMAC 等常用密码学算法。同时，Zephyr 正在向 PSA Crypto API（Platform Security Architecture）迁移——这是 ARM 制定的标准化加密接口，让应用代码可以无缝切换后端实现（软件加密 / 硬件加密引擎）。

安全启动（Secure Boot）

安全启动就像"出厂封条"——设备上电后，bootloader 会验证固件签名，只有签名正确的固件才能执行。这防止了攻击者刷入恶意固件。Zephyr 通过 MCUboot 实现安全启动（详见下一节）。

TLS / DTLS 通信加密

网络通信如果不加密，就像寄明信片——任何人都能偷看内容。TLS（传输层安全）为 TCP 通信加密，DTLS 为 UDP 通信加密。Zephyr 的 net_tls 子系统让 socket 编程和 TLS 无缝结合。

conf 
# prj.conf — 启用安全特性

# 启用 mbedTLS
CONFIG_MBEDTLS=y
CONFIG_MBEDTLS_BUILTIN=y

# 启用 PSA Crypto API
CONFIG_PSA_CRYPTO=y

# 启用 TLS（用于 TCP 通信加密）
CONFIG_NET_SOCKETS=y
CONFIG_NET_SOCKETS_TLS=y
CONFIG_MBEDTLS_TLS_ENABLED=y

# 安全启动相关
CONFIG_BOOTLOADER_MCUBOOT=y

# 硬件加密引擎（如果芯片支持）
CONFIG_CRYPTO=y

小贴士：如果目标芯片有硬件加密引擎（如 STM32 的 CRYP、Nordic 的 CC310），启用硬件加速可以大幅提升加密性能并降低 CPU 占用。通过 PSA Crypto API，应用代码无需修改即可自动使用硬件加速。

MCUboot 与 OTA 固件升级

OTA（Over-The-Air）升级就像手机系统更新——不需要数据线，通过网络就能给设备刷新固件。MCUboot 是 Zephyr 生态中广泛使用的安全引导加载程序，它负责两件事：验证固件完整性和管理固件升级流程。

MCUboot 核心概念

  • 镜像格式：MCUboot 要求固件打包为特定格式（包含头部信息和签名），通过 imgtool 工具签名打包
  • 签名验证：每次启动前，MCUboot 用公钥验证固件签名，确保固件未被篡改
  • Single Bank：只有一个固件槽，升级时直接覆盖旧固件（风险较高，断电可能变砖）
  • Dual Bank：有两个固件槽（primary + secondary），新固件先写入 secondary 槽，验证通过后交换启动（安全，断电不影响旧固件）

DFU 传输方式

新固件怎么传到设备上？Zephyr 支持多种传输通道：

  • BLE：通过蓝牙低功耗传输，适合无 Wi-Fi 的便携设备
  • UART：通过串口传输，开发调试阶段最常用
  • USB：通过 USB 接口传输，速度快
  • Wi-Fi / Ethernet：通过网络传输，适合已联网的 IoT 设备

这些传输方式都基于 SMP（Simple Management Protocol）协议，通过 mcumgr 命令行工具管理固件升级过程。

conf 
# prj.conf — 启用 MCUboot 与 DFU

CONFIG_BOOTLOADER_MCUBOOT=y
CONFIG_IMG_MANAGER=y
CONFIG_IMG_ERASE_PROGRESSIVELY=y

# 启用 SMP 协议（通过 BLE/UART/USB 传输固件）
CONFIG_MCUMGR=y
CONFIG_MCUMGR_CMD_IMG_MGMT=y
CONFIG_MCUMGR_CMD_OS_MGMT=y

# 通过 UART 传输
CONFIG_MCUMGR_TRANSPORT_UART=y

# 通过 BLE 传输
# CONFIG_MCUMGR_TRANSPORT_BT=y
C 
/* Device Tree 中定义 flash 分区 */
/* 通常在 boards/<board>.dts 中已预定义 */
/* primary-slot: 当前运行的固件 */
/* secondary-slot: 存放待升级的新固件 */

/* 应用代码：确认当前固件，标记升级成功 */
int confirm_firmware(void)
{
    if (boot_is_img_confirmed()) {
        printk("固件已确认，无需重复操作\n");
        return 0;
    }

    int ret = boot_write_img_confirmed();
    if (ret == 0) {
        printk("固件确认成功，升级完成！\n");
    } else {
        printk("固件确认失败: %d\n", ret);
    }
    return ret;
}

重要：OTA 升级后，新固件必须主动调用 boot_write_img_confirmed() 确认升级成功。否则 MCUboot 会在下次重启时回滚到旧固件——这是一种安全保护机制，防止新固件无法正常运行导致设备"变砖"。

文件系统

文件系统让嵌入式设备拥有了"文件柜"——你可以按名字存取数据，不用关心底层 flash 芯片的擦写细节。Zephyr 支持多种文件系统，最常用的是 LittleFS 和 FATFS。

LittleFS —— 嵌入式首选

LittleFS 专为嵌入式 flash 存储设计，就像一个抗震文件柜——即使突然断电，文件也不会损坏。它的三大核心优势：

  • 掉电安全（Power-fail safe）：写入操作是原子性的，断电不会导致文件系统损坏
  • 磨损均衡（Wear leveling）：均匀使用 flash 各个区块，延长 flash 寿命
  • 低 RAM 占用：只需要极少的 RAM 即可运行，适合资源受限的 MCU

FATFS —— SD 卡兼容

FATFS 是经典的 FAT16/FAT32 文件系统实现，最大优势是与 PC 兼容——拔出 SD 卡插到电脑上就能直接读取。但 FATFS 不具备掉电安全和磨损均衡能力，适合有 SD 卡插槽的设备。

文件操作 API

Zephyr 提供了 POSIX 风格的文件操作 API，和 Linux 上的用法几乎一样：

  • fs_open() — 打开文件
  • fs_read() — 读取文件
  • fs_write() — 写入文件
  • fs_close() — 关闭文件
  • fs_unlink() — 删除文件
  • fs_mkdir() — 创建目录
  • fs_stat() — 获取文件信息
C 
/* prj.conf */
/* CONFIG_FILE_SYSTEM=y      */
/* CONFIG_FILE_SYSTEM_LITTLEFS=y */
/* CONFIG_FLASH=y             */
/* CONFIG_FLASH_PAGE_LAYOUT=y */

#include <zephyr/fs/fs.h>
#include <zephyr/fs/littlefs.h>

FS_LITTLEFS_DECLARE_DEFAULT_CONFIG(storage);

static struct fs_mount_t mount_point = {
    .type = FS_LITTLEFS,
    .fs_data = &storage,
    .storage_dev = (void *)FLASH_AREA_ID(storage),
    .mnt_point = "/lfs",
};

void fs_example(void)
{
    /* 挂载文件系统 */
    int ret = fs_mount(&mount_point);
    if (ret < 0) {
        printk("挂载失败: %d\n", ret);
        return;
    }

    /* 写入文件 */
    struct fs_file_t file;
    fs_file_t_init(&file);
    ret = fs_open(&file, "/lfs/hello.txt", FS_O_WRITE | FS_O_CREATE);
    if (ret >= 0) {
        char *msg = "Hello, LittleFS!";
        fs_write(&file, msg, strlen(msg));
        fs_close(&file);
    }

    /* 读取文件 */
    fs_file_t_init(&file);
    ret = fs_open(&file, "/lfs/hello.txt", FS_O_READ);
    if (ret >= 0) {
        char buf[64] = {0};
        fs_read(&file, buf, sizeof(buf));
        printk("读取内容: %s\n", buf);
        fs_close(&file);
    }
}

小贴士：flash 分区（partition）需要在 Device Tree 中定义。LittleFS 需要一个独立的 flash 分区来存储文件数据。确保分区大小足够，且不要和固件区域重叠。

Shell 命令行调试

Shell 就像设备的"远程控制台"——通过串口连接设备后，你可以输入命令查看状态、修改参数、触发操作，就像在 Linux 终端里操作一样。这是嵌入式开发中最实用的调试手段之一。

Shell 子系统

Zephyr 的 Shell 子系统提供了完整的命令行框架：命令注册、参数解析、子命令、Tab 自动补全、命令历史等。它支持多种传输后端（UART、RTT、Telnet），最常用的是 UART。

自定义命令

通过 SHELL_CMD_REGISTER 宏注册自定义命令，就像给遥控器添加一个新按钮——按下按钮（输入命令），执行对应的操作（回调函数）。

C 
#include <zephyr/shell/shell.h>

/* 命令处理函数 */
static int cmd_led_on(const struct shell *sh, size_t argc,
                       char **argv)
{
    if (argc > 1) {
        shell_print(sh, "点亮 LED %s", argv[1]);
    } else {
        shell_print(sh, "点亮默认 LED");
    }
    return 0;
}

static int cmd_led_off(const struct shell *sh, size_t argc,
                        char **argv)
{
    shell_print(sh, "熄灭 LED");
    return 0;
}

/* 注册子命令 */
SHELL_STATIC_SUBCMD_SET_CREATE(sub_led,
    SHELL_CMD(on,  NULL, "点亮 LED",  cmd_led_on),
    SHELL_CMD(off, NULL, "熄灭 LED",  cmd_led_off),
    SHELL_SUBCMD_SET_END
);

/* 注册顶层命令：led on / led off */
SHELL_CMD_REGISTER(led, &sub_led, "LED 控制", NULL);

注册后，在串口终端中输入 led on 1 即可点亮 LED 1，输入 led off 熄灭 LED。Shell 还支持 Tab 衮补全——输入 led 后按 Tab，会自动列出 on 和 off 两个子命令。

小贴士：Shell 命令是开发调试的利器，但生产环境中要注意安全——建议通过 CONFIG_SHELL_MINIMAL 或权限控制限制可用命令，避免用户误操作导致设备异常。

日志系统

日志系统是嵌入式开发的"黑匣子"——它记录程序运行过程中的关键信息，帮助你在出问题时回溯定位。和简单的 printk() 不同，Zephyr 的日志系统支持分级过滤、模块标识、多种后端输出，是专业级的日志方案。

日志级别

日志按严重程度分为四个级别，就像医院的分诊制度——急症优先处理：

  • LOG_ERR — 错误：必须立即处理的严重问题
  • LOG_WRN — 警告：可能引发问题的异常情况
  • LOG_INF — 信息：重要的运行状态信息
  • LOG_DBG — 调试：仅开发阶段需要的详细信息

运行时过滤

日志可以在编译时设置默认级别，也可以在运行时动态调整。比如开发时开启 DBG 级别看所有日志，生产时只保留 ERR 级别。通过 Shell 命令 log level 可以实时调整。

日志后端

日志输出到哪里？Zephyr 支持多种后端：

  • UART：最常用，通过串口输出到 PC 终端
  • RTT：SEGGER RTT，速度比 UART 快得多，适合调试器连接时使用
  • 自定义后端：可以将日志写入 flash、发送到网络服务器等
C 
#include <zephyr/logging/log.h>

/* 注册日志模块，设置模块名和默认级别 */
LOG_MODULE_REGISTER(my_app, LOG_LEVEL_INF);

void sensor_task(void)
{
    LOG_INF("传感器任务启动");

    int ret = sensor_sample_fetch(sensor_dev);
    if (ret < 0) {
        LOG_ERR("传感器读取失败: %d", ret);
        return;
    }

    struct sensor_value temp;
    sensor_channel_get(sensor_dev, SENSOR_CHAN_TEMPERATURE, &temp);

    if (temp.val1 > 80) {
        LOG_WRN("温度过高: %d.%06d°C", temp.val1, temp.val2);
    }

    LOG_DBG("温度: %d.%06d°C", temp.val1, temp.val2);
}

性能提示：LOG_DBG 宏在编译时如果日志级别不够会被完全消除（零开销），不会占用任何代码空间或运行时间。所以放心地在代码中添加调试日志，生产构建时它们会自动消失。

Settings 持久化存储

Settings 子系统是设备的"备忘录"——它帮你把配置参数持久化保存到 flash 中，断电不丢失。下次开机时自动加载，就像手机记住你的 Wi-Fi 密码一样方便。

键值对存储

Settings 采用层级键值对模型，键名用斜杠分隔层级，类似文件路径。比如 net/wifi/ssid、sensor/interval。每个键对应一个值（二进制数据），读写都非常简洁。

存储后端

Settings 支持两种 flash 后端：

  • FCB（Flash Circular Buffer）：循环写入，适合频繁更新的场景，自动垃圾回收
  • NVS（Non-Volatile Storage）：名字值存储，API 更简洁，适合一般用途
C 
#include <zephyr/settings/settings.h>

/* 定义要保存的配置项 */
static int sensor_interval = 1000;  /* 默认 1000ms */
static char device_name[32] = "zephyr-device";

/* 加载回调：从 flash 读取值时触发 */
static int settings_handler(const char *key, size_t len,
                           settings_read_cb read_cb,
                           void *cb_arg)
{
    if (strcmp(key, "interval") == 0) {
        return read_cb(cb_arg, &sensor_interval, sizeof(sensor_interval));
    }
    if (strcmp(key, "name") == 0) {
        return read_cb(cb_arg, device_name, sizeof(device_name));
    }
    return -ENOENT;
}

static struct settings_handler my_conf = {
    .name = "myapp",
    .h_set = settings_handler,
};

void settings_example(void)
{
    /* 注册 handler */
    settings_register(&my_conf);
    settings_subsys_init();

    /* 从 flash 加载所有 myapp/* 配置 */
    settings_load();

    /* 修改并保存配置 */
    sensor_interval = 500;
    settings_save_one("myapp/interval",
                      &sensor_interval, sizeof(sensor_interval));

    printk("采集间隔: %dms, 设备名: %s\n",
           sensor_interval, device_name);
}

注意：settings_save_one() 每次调用都会触发 flash 写入。如果需要保存多个配置项，建议使用 settings_save() 一次性保存所有修改，减少 flash 写入次数，延长 flash 寿命。

用户空间与权限隔离

用户空间就像操作系统的"安全隔离舱"——普通应用程序在隔离舱内运行，无法直接访问内核或其他应用的内存，所有敏感操作必须通过系统调用（syscall）请求内核执行。这就像乘客不能进驾驶舱，只能通过乘务员传话给机长。

核心概念

  • CONFIG_USERSPACE：启用用户空间支持，需要硬件有 MPU（Memory Protection Unit）
  • Supervisor 模式：内核线程运行的模式，可以访问所有内存和硬件
  • User 模式：应用线程运行的模式，只能访问自己的内存域
  • 内存域（Memory Domain）：一组内存分区（partition）的集合，定义了用户线程可以访问的内存范围
  • 系统调用（Syscall）：用户线程请求内核服务的唯一通道，Zephyr 自动生成 syscall 桩代码

MPU 隔离

MPU 是硬件级别的内存保护单元，可以设置内存区域的访问权限（读/写/执行）。Zephyr 利用 MPU 实现：内核代码和数据对用户线程不可写、每个用户线程只能访问自己的栈和授权的内存分区、设备寄存器只能通过内核 API 访问。

何时使用？用户空间主要适用于安全要求高的场景（如 IoT 网关处理不可信数据）。它有性能开销——每次 syscall 都要切换上下文。对于资源受限或对实时性要求极高的场景，不建议开启。

模块化系统

Zephyr 的模块化系统就像乐高积木的"零件仓库"——你可以从仓库中挑选需要的零件（模块），组装成自己的项目。每个模块是一个独立的外部代码库，通过 west 管理器统一管理版本和依赖。

West 模块

West 是 Zephyr 的元工具（meta-tool），它不仅管理 Zephyr 主仓库，还管理所有外部模块。在 west.yml 中声明模块的 Git 仓库地址和版本，west update 就会自动拉取所有模块到正确版本。

常用模块

  • hal_stm32：STM32 系列的 HAL 库和 CMSIS 支持
  • mbedtls：mbedTLS 加密库，提供 TLS 和密码学功能
  • mcuboot：安全引导加载程序
  • lvgl：Light and Versatile Graphics Library，GUI 开发
  • nanopb：Protocol Buffers 的嵌入式实现

自定义模块

你可以将自己的库封装为 Zephyr 模块。只需在模块根目录创建 zephyr/module.yml 文件，声明模块的源码路径和头文件路径（MODULE_INCLUDE），然后在 west.yml 中添加模块引用即可。Zephyr 构建系统会自动发现并集成模块中的源码和 Kconfig 配置。

小贴士：模块和 Zephyr 主仓库版本需要匹配。升级 Zephyr 版本时，记得同时运行 west update 更新所有模块到兼容版本，避免 API 不兼容导致的编译错误。

Zephyr 测试框架

ztest 是 Zephyr 内置的单元测试框架，就像代码的"体检中心"——你为每个功能编写测试用例，ztest 自动运行所有测试并报告通过/失败。写测试虽然费时间，但它是代码质量的保险：修改代码后跑一遍测试，立刻知道有没有引入回归问题。

核心 API

  • ztest_test_suite() — 定义测试套件（一组相关测试）
  • ztest_unit_test() — 注册单元测试用例
  • ztest_run_test_suite() — 运行测试套件
  • ztest_assert_* — 断言宏，条件不满足时标记测试失败
  • setup() / teardown() — 每个测试前后的准备和清理函数

常用断言

断言宏 说明
zassert_true(cond, msg) 条件为真
zassert_false(cond, msg) 条件为假
zassert_equal(a, b, msg) a 等于 b
zassert_not_equal(a, b, msg) a 不等于 b
zassert_null(ptr, msg) 指针为 NULL
zassert_not_null(ptr, msg) 指针不为 NULL
zassert_mem_equal(a, b, size, msg) 内存内容相等

#include <zephyr/ztest.h>

/* 被测函数 */
static int celsius_to_fahrenheit(int celsius)
{
    return (celsius * 9 / 5) + 32;
}

/* 测试用例：正常温度转换 */
static void test_celsius_to_fahrenheit(void)
{
    zassert_equal(celsius_to_fahrenheit(0), 32,
                  "0°C 应为 32°F");
    zassert_equal(celsius_to_fahrenheit(100), 212,
                  "100°C 应为 212°F");
    zassert_equal(celsius_to_fahrenheit(-40), -40,
                  "-40°C 应为 -40°F");
}

/* 测试用例：边界值 */
static void test_extreme_values(void)
{
    zassert_true(celsius_to_fahrenheit(-273) < -400,
                 "绝对零度附近温度应极低");
}

{
    /* 初始化测试环境 */
}

/* teardown：每个测试后执行 */
static void test_teardown(void *fixture)

    /* 清理测试环境 */
}

ZTEST_SUITE(temperature_tests, NULL,
